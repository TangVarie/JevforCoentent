# Jev 在这套东西里到底怎么被用（一页）

> 回答两个问题：Jev 具体在哪一步、以什么形式介入；评论怎么写。docs/31 讲的是全局，这一页只讲机制，能对着代码逐行核。

## 1. 一次调用长什么样

整个仓库对 Jev 只做一种事：把一段文字和几道带定义的闭集题一起发过去，拿回每道题的答案和概率。下面是今天实跑里
途鸽那篇帖子下第一条评论的请求和返回（`jev-comment-unit/raw_comment_v0.3.json`，原样，只删了帖子正文以省篇幅）：

一次调用，2,078 个输入 token，七道题一起答，不到一秒。它没有写一个字，也没有解释一句理由；理由就是这七个答案本身：
背书体、点了名、没接住帖子（0.29）、只有一个模糊情境、文案腔（0.99）、读者拿不到东西、像安排的（0.74）。
代码把这份返回翻成内部表示（`banks.interpret`）：每题一个 `answer`、一个「所选答案的概率」`p`、一个歧义标记（选择题第一名 < 0.60 或前两名差 < 0.20，是非题落在 0.35–0.65）。

整个仓库所有位置——特征层、评论、借卡、入库判定、二审、外部语料——发出去的都是这一种请求；变的只有三样：**state 里放什么**（一篇笔记切好的四段、一段、一条评论加它的帖子、一组评论、一条搜索摘要）、**用哪份题库**、**答案拿回来做什么**。

## 2. 答案拿回来做的三件事

**记账**。每个答案变成 `truth_vault.note_feature_answers` 的一行：subject、题号、题库版本与校验和、答案、概率、证据句、run_tag（`core.ledger_rows`）。这是飞轮那一侧的用法：闸二拿它算「哪些特征和爆文相关」。

**分流**。把答案和「这个位置想要的答案」比：平台题库 `efficacy_claim` 想要「否」，答了「是」就是硬伤；评论位想要「补充经验」，答了「亲历背书」就是硬伤；分诊题 `on_topic` 答「否」就丢弃。硬伤只是一个二元判断加一个概率，谁来处理由调用方定（影子期只记不拦，D-#4）。

**修改单**。硬伤不是退回一句「不够真」，而是把题号、现在的答案与概率、要改成什么、那个选项的定义（篇级还有依据句）拼成一条指令，例如：

> 「这条评论的说话方式更像哪一种？」现在判「文案腔」（0.99），要改成「随手口语/认真分享」：短、省略、有语气词或错字，像刷手机时随手打的 ／ 用自己的话讲一件具体发生过的事，有过程或细节，像认真回陌生人一条

这条指令交给便宜的生成模型去改，改完再判，直到过或预算用完。**判定端用的定义和生成端拿到的定义是同一段文字**，所以「好」不再是形容词，是「这 N 题都过」。

## 3. 一篇稿子的回路（`judge/loop.py`）

写前：brief 里的意图清单、能写成闭集的硬约束、分到的切口，编译成项目题库（`compile_project_bank`）。这一步没有调用 Jev，只是把 brief 变成题。

写中：生成端出 k 版，每版跑 fq + 平台 + 项目题库（每个题库各一次调用，答「是」的题再各一次证据调用，最多 6 次；勘误：原写「一次调用」），硬伤数 × 100 + 目标画像不符 × 10 + 歧义 × 1，取最小的那版（`best_of_k`）。

写后：不过就判段（人感题库六题 + 「这一段承担哪个意图」），修改单落到具体段、具体句；便宜模型只改指到的地方；再判（`repair_plan → repair → judge_draft`）。

今天两篇真实笔记的实跑：每篇 10–12 次调用、4.5 秒；「效果是真的绝…立马就压住了」被平台题库判疗效暗示 0.68，「省下的烟钱都够给老婆买个包」被项目题库判省钱 0.77，都带依据句；段级分布给出无产品意图段 83%、产品第一次出现在第 4 段、有摩擦、无总结式收尾。生成端是可插拔适配器（Anthropic 兼容端点），本轮没接真实生成端。

## 4. 评论的回路（`judge/comments.py`，本轮新加）

之前只有 `judge_comments`（判一批候选、打旗），没有从「要什么」到「出来什么」的回路。现在和稿子的回路同构：

**写前是评论位（Slot）**。一位就是一条评论的目标画像：要做什么（提问 / 补充经验 / 贴主回复答疑…）、能不能点名、要不要接住帖子里具体的事、读者能拿到什么、细节至少到哪一档、运营侧意图填哪一个。默认一组是：提问 ×2（读者位，不点名，不强求接帖）、补充经验 ×1（读者位，不点名，要接帖、要有情境、要给读者判断依据）、贴主回复答疑 ×1（回第一条提问，可点名，要给可行动信息）。brief 可以换成自己的位（`slots_from_brief`）。

默认组里没有「亲历背书 / 旁观推荐」这一位：读者侧题库把这两类直接路由进高风险复核（题库 `feeds` 写明），回路里它们只会被换掉，不会被修得更像。评论区的营销职能是承接——回答、补充、指路——不是背书；途鸽 7 条的实跑里五条背书体全部被判「像安排的」（0.73–0.78），唯一的读者提问 0.43，这就是你截图时说的「一眼看穿」在数字上的样子。有贴主回复，评论区那道 `has_friction` 就有着落，不用造质疑。

**写中**：每一位生成端出 k 条候选，逐条跑读者侧 7 题 + 运营侧 2 题，按硬伤排序取一条（`best_of_k_comment`）。

**写后**：硬伤 → 修改单（题号 + 概率 + 要改成什么 + 定义，占位符已按本篇填好）→ 生成端只改这一条 → 再判（`comment_repair_plan → repair_comment`）。

**成组**：一组选定后整体过评论区 4 题（夸的比例、同一句式、有没有摩擦、整体像不像安排的），加代码算的点名条数、背书条数；不过就指出哪一位要换（`judge_thread → thread_repair_plan`），换掉的位若有人回复，回复位一起重出。

**整条** `produce_comments` 把上面串起来，返回评论组、每条的画像与旗子、评论区画像、每一步的轨迹。按题干变的部分（帖子要点、主体是机构还是产品）通过 `fill_for(post)` 填进题库 v0.4 的占位符，途鸽用例填回去与 v0.3 逐字相同（测试钉住），所以金标准 cg-v0.2 仍然有效。

下面是流程演示的轨迹（假 Jev 按关键词给答案，数字不是模型的；真实数字要等密钥）：exp 位两条候选都是背书体（各 7 处硬伤，分数 720），修改单下发后生成端给回「我也是文科，当时也反复问了简历是不是他们写，后来四版改下来才踏实」，再判：补充经验、不点名、接住帖子、具体、认真分享、判断依据；三条一组的评论区：夸的少数、不同句式、有摩擦（贴主回复）、不像安排的；15 次调用。

三个入口：写手 MCP（`comment_repair_plan_for` 判一条给修改单、`judge_thread` 判一组、`judge_comments` 批量打旗）；HTTP `/judge` 用 `comment_reader_v0.4` 加 `fill`；三省六部的 `comment_seeds` 过同一套。

## 5. 本仓不做、生成端做

本仓没有任何一条「怎么写」的 prompt；只有修改单的格式（`loop.repair_prompt` / `comments.comment_repair_prompt`）：帖子、候选、这一位的要求、修改单，要求只改指到的地方、只输出改后的原文。第一稿怎么出（人设、口吻、素材）是三省六部提示词系统和写手的事，通过 `prompt_for(post, slot)` 传进来。Jev 只回答「它是不是」，不回答「怎么让它是」——后者由定义和生成端一起完成。

## 6. 还没做的

真实生成端没接（`AnthropicCompatGenerator` 现成，接三省六部的中转站即可）；评论回路没联网跑过（密钥不在这个环境里）；评论金标准只有途鸽一篇（求职留学），大健康品类要按 v0.4 的占位符另标一组。
